Profiles, roles, and caller identity

A profile is a local name for AWS settings. A role defines AWS permissions. Caller identity shows which account and role a command uses.

List local profile names
aws configure list-profiles

You can keep several profiles. Use --profile for AWS CLI commands. The Terraform provider uses profile = "terraform-dev".

MFA and permission limits

You reported that MFA was completed during login. Do not register the same device again. AWS can ask for MFA at a later sign-in.

To inspect devices, open the AWS access portal. Select your name. Select My devices. Register a device if none exists. An administrator controls the MFA policy.

AmazonEC2FullAccess is broad access. It is not a least-privilege policy. This DNS instance needs no IAM role. Instance roles can require iam:PassRole. IAM creation, S3 state, and custom KMS keys can require extra permissions.

The answer returns to your Mac. Both firewalls must allow the request. Routes and network ACLs must also permit the traffic.

The current BIND file has two upstreams. The README also mentions 8.8.8.8. That third server is absent from the actual configuration.

BIND uses forward only. It sends unresolved queries to the configured upstreams. Their order does not guarantee primary/secondary use. The config disables DNSSEC validation.

EC2 bootsUbuntu starts
→
Cloud-initWrites embedded files
→
bootstrap.shPackages, BIND, UFW
→
Health checkHost checks only

Cloud-init copies files to /opt/dns-forwarder. It saves client settings in /etc/dns-forwarder/settings.json. It then runs bootstrap as root. Terraform has no SSH provisioner.

1. Wait for setup, then check the host
PUBLIC_IP=$(terraform -chdir=terraform output -raw public_ip)
chmod 400 ~/PEM/dns_forwader_test_pem.pem
ssh -i ~/PEM/dns_forwader_test_pem.pem ubuntu@"$PUBLIC_IP" \
  'sudo cloud-init status --wait && sudo /opt/dns-forwarder/scripts/health-check.sh'

The host check validates BIND configuration and service state. It checks TCP and UDP listeners. It tests local and upstream DNS. It checks UFW rules. It does not prove external access.

2. Test from your Mac · selected transport

Expect status: NOERROR. Expect an A record in the answer. The SERVER line must show your instance's current public IP. Test both UDP and TCP.

Rerun bootstrap on the existing instance
Changes BIND and UFW on the host
PUBLIC_IP=$(terraform -chdir=terraform output -raw public_ip)
ssh -i ~/PEM/dns_forwader_test_pem.pem ubuntu@"$PUBLIC_IP" \
  'sudo /opt/dns-forwarder/scripts/bootstrap.sh'

Bootstrap already runs at first boot. Rerun it only when needed. It uses saved settings. It makes backups. It validates configuration and restarts BIND.

UFW rules are additive. A rerun does not remove old rules. A smaller CIDR list does not revoke existing access. Inspect old rules before you remove them.

Files on the server are copies from deployment time. Local repo edits do not automatically update those copies. Deploy updated files or review a Terraform replacement plan.

Read logs and diagnostics
Read-only checks on Ubuntu
PUBLIC_IP=$(terraform -chdir=terraform output -raw public_ip)
ssh -i ~/PEM/dns_forwader_test_pem.pem ubuntu@"$PUBLIC_IP" \

06 / Customer onboarding

Same code. One deployment per customer.

Give each customer separate settings and state. Each customer gets an instance, security group, and Elastic IP. A new deployment does not replace the first customer's instance.

Shared Terraform codeOne maintained definition
→
Customer ASettings A + state A
EC2 A + Elastic IP A
/
Customer BSettings B + state B
EC2 B + Elastic IP B

Small start: CLI workspaces

Use one workspace per customer. Use one explicit tfvars file per customer. Pass that file to every plan.

A workspace does not select a tfvars file for you. Always check the workspace and customer file.

Production: separate root configurations

Move shared resources into a reusable module. Give each customer a small root configuration. Use a separate backend state key and appropriate access controls.

Use a remote backend with locking for team work. Agree on the backend before migrating local state.

A workspace separates state, not AWS permissions.

Both deployments still use the same account, provider, and VPC in this example. Use separate accounts or network boundaries when customer requirements demand stronger isolation.

Build an onboarding command example

Use lowercase letters, digits, and hyphens. Start with a letter.

Before the plan, edit the customer tfvars file. Keep your admin IP in admin_cidr. Set dns_client_cidrs to that customer's public source IPs. Enable Elastic IP. Choose the required instance size.

Add a customer tag. For example: tags = { Environment = "dev", Customer = "acme" }. The current resource Name tag stays dns-forwarder. The Customer tag helps identify each copy.

Do not change only the customer variables in the first customer's workspace. That changes the first deployment. A new customer needs a separate state.

Why not use one large for_each map?

A module can use for_each to create one instance per customer. All customers then share one state and plan. Removing a customer from the map can propose its destruction.

For independently managed customer instances, separate states keep the scope of each plan smaller. Choose the model before you automate onboarding.

This is a design and command example. No customer workspace, backend, or infrastructure was created. Sources: workspace limits · reusable modules · S3 backend and locking.

07 / Stable public address

An Elastic IP follows the deployment.

An Elastic IP is an allocated public IPv4 address. It can stay the same after stop/start or instance replacement. It must remain allocated.

TerraformAllocate an address
→
Elastic IPManaged AWS allocation
→
Existing EC2Associate the address
First set this in terraform/terraform.tfvars
associate_elastic_ip = true
Plan, review, then attach
terraform -chdir=terraform plan -out=elastic-ip.tfplan
# Expect one Elastic IP to add. Check for other changes.
terraform -chdir=terraform apply elastic-ip.tfplan
terraform -chdir=terraform output -raw public_ip
The connection address changes.

The ordinary address is replaced by the Elastic IP. An SSH connection can drop. Reconnect with the current Terraform output. Update clients that use the old address.

The recorded Elastic IP plan added one resource. It did not replace EC2. The current tfvars already enables this option. Attachment was not confirmed in our transcript.

An Elastic IP does not make your laptop IP stable. Client source restrictions still use your current public IP. A destroy releases the managed Elastic IP. You cannot rely on getting the same address later.

SSO expired, or AWS shows the wrong identity

Sign in again with aws sso login --profile terraform-dev. Check caller identity before a plan.

If Terraform uses an unexpected identity, check credential environment variables. They can override profile credentials. Do not print secrets. Remove stale exported access-key variables from the terminal when needed.

Clear key-based environment overrides when appropriate
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
aws sts get-caller-identity --profile terraform-dev
SSH times out or DNS has no answer

Check the current Terraform public IP. Check your current client public IP. Compare it with the allowed CIDRs.

Check the security group. Check UFW. Check cloud-init logs. Check the subnet route and network ACL. The route must permit Internet access.

If SSH reports Permission denied (publickey), use the Ubuntu user and the matching private key. Never paste the private key into a chat.

A custom network ACL is stateless. It needs query and reply traffic in both directions. Security groups are stateful.

This was the first deployment. The repo already expects an existing VPC and subnet. This keeps the test focused on EC2 and DNS.
